User Accreditation API

Welcome to the developer portal of the User Accreditation Service. Administrators use the API to submit accreditations and decide on them, and the client-facing app uses it to read the current status of a user's accreditations.

About the Project

The service is built with Quarkus on Java 21. Writes are event-first: the API checks a request against the current state, publishes an event to Kafka and answers 202 Accepted. A consumer applies the events to PostgreSQL, which serves the reads. Kafka keeps every event, so the topic is also the audit log of every accreditation.

Key Features

  • Submission: POST /user/accreditation takes the user, the accreditation type and a PDF document, and starts the accreditation as PENDING
  • Finalization: PUT /user/accreditation/{accreditationId} confirms, fails or expires an accreditation, as far as its lifecycle allows
  • Client Status: GET /user/{userId}/accreditation returns every accreditation of a user, served from a Redis cache
  • History: every status change of an accreditation, with its origin and time
  • Automatic Expiry: CONFIRMED accreditations expire 30 days after their last update
  • Event Log: Kafka events keyed by user, applied in order, duplicates skipped, with a dead-letter topic for the ones that keep failing
  • Validation: strict request checks and one error body with field errors and a trace id
  • Resilience: consumer retries, circuit breakers for Kafka and PostgreSQL, rate limits and graceful shutdown
  • Metrics & Monitoring: Prometheus metrics, health checks and a trace id on every log line

Getting Started

Start everything with ./run.sh from the project root. The endpoints are under http://localhost:9999/api/v1; the API page lists them and can send requests to them. The OpenAPI document is at /q/openapi.

User Accreditation API

Submitting and finalizing answer 202: the change is published to Kafka first and shows up once the consumer has written it to the database. Every response carries an X-Request-Id header, which error bodies repeat as trace_id. Times are in Europe/Malta time, with the offset of that day.

Lifecycle and Rules

An accreditation starts as PENDING when it is submitted. An administrator's decision or the expiry job moves it on. The rules are checked twice: by the API when a request comes in, and by the consumer against the latest state before anything is written.

Statuses

FromToHow
PENDINGPOST /user/accreditation
PENDINGCONFIRMEDPUT with outcome CONFIRMED
PENDINGFAILEDPUT with outcome FAILED
CONFIRMEDEXPIREDPUT with outcome EXPIRED, or the expiry job after 30 days

FAILED and EXPIRED are final. Any other change, including one to the status the accreditation already has, is answered with 409 Conflict, so a PENDING accreditation can't be expired through the API.

Rules

  • One Pending Accreditation per User: while a user has a PENDING accreditation, another submission gets 409. A unique index in PostgreSQL holds the same rule.
  • Automatic Expiry: a job expires CONFIRMED accreditations whose last update is more than 30 days old. It runs when the service starts and then every hour, and its changes have the origin SYSTEM_EXPIRY.
  • Concurrent Decisions: a status change carries the status it was decided on and is applied only if the accreditation still has it. When two administrators decide at the same time, the first change wins and the consumer rejects the other.
  • Accepted, Then Applied: POST and PUT answer once the event is in Kafka. The change shows up a moment later, so right after a user's first submission the client endpoint can still answer 404.

Validation

Unknown or missing fields, wrong types and malformed JSON get 400. Like every error, it comes with message, detail and trace_id; validation errors also list the fields under errors.

Delivery

  • Duplicates: Kafka delivers at least once, so the consumer skips an event whose event_id it has already applied.
  • Retries: a failing event is tried three more times, 2, 4 and 8 seconds apart.
  • Dead-Letter Topic: accreditation-status-events-dlq gets the events that still fail, and right away the messages that aren't valid JSON. The headers dead-letter-reason, dead-letter-topic, dead-letter-partition and dead-letter-offset tell why and where from. It keeps its records forever as well.
  • Rejections: an event that no longer fits the stored state, such as the losing one of two decisions, is not an error. It is logged and counted, and doesn't go to the dead-letter topic.

Limits and Monitoring

How much traffic the API takes, what it answers while Kafka or PostgreSQL is down, and where to look when something goes wrong.

Rate Limits

EndpointRequests a second
POST /user/accreditation10
PUT /user/accreditation/{accreditationId}10
GET /user/accreditation/{accreditationId}/history10
GET /user/{userId}/accreditation100

Each endpoint has its own limit over a rolling one-second window. Beyond it the answer is 429 with Retry-After. Rejected requests count towards the window too, so wait as long as Retry-After says.

When Kafka or PostgreSQL Is Down

  • Kafka: when Kafka doesn't acknowledge an event, the producer gives up within a few seconds and the API answers 503 with Retry-After: 5. The event is not sent later.
  • Circuit Breakers: Kafka and PostgreSQL each have one. When at least half of the last 10 calls failed, it opens for 10 seconds, and requests get 503 with Retry-After: 10 at once.
  • Consumer: its retries take longer than a circuit stays open, so a short database outage doesn't send events to the dead-letter topic.
  • Shutdown: when the service stops, requests already running get up to 30 seconds to finish.

Tracing a Request

Every response carries an X-Request-Id header, error bodies repeat it as trace_id, and every log line of the request has it. The consumer's log lines have event_id and accreditation_id instead.

Metrics

/q/metrics serves the metrics in Prometheus format. The Prometheus started by Docker Compose reads them every 5 seconds, at http://localhost:9090, and Grafana shows them on a dashboard at http://localhost:3000.

MetricCounts
accreditation_submissions_total{type}accepted submissions
accreditation_finalizations_total{outcome}accepted decisions
accreditation_expiries_totalexpiries published by the job
accreditation_projected_events_total{result, reason}what the consumer did with each event: applied, duplicate or rejected, and why
accreditation_dead_lettered_events_total{reason}messages sent to the dead-letter topic: failed or unreadable

HTTP, JVM and Kafka client metrics come with them, and so do the retry, circuit breaker and rate limit metrics of SmallRye Fault Tolerance.

Health

/q/health reports liveness and readiness. /q/health/ready is UP once PostgreSQL, Redis and Kafka can be reached; run.sh waits on it.
